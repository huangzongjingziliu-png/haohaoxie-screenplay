# 商业化方案：免费开源 + 商店付费同步与模板

更新日期：2026-11-16
依据：用户已确认方向「开源版免费全功能（自带 API key）；商店版付费，卖 iCloud 同步与内置模板/技能库；1.0 免费上架走通审核，1.1 再加付费」。
标注约定：**【已核实】**＝仓库代码或 Apple 公开文档可查；**【判断】**＝我的分析，不是事实；**【待核实】**＝需要你或律师确认，尤其是价格与条款数字。

## 1. 为什么付费点是同步与模板，而不是软件本身

**【已核实】** 仓库根 `LICENSE` 为 MIT，任何人都可以合法编译、改名、分发这份代码（详见 [open-source-and-app-store.md](open-source-and-app-store.md)）。因此「卖软件本体」在事实上不可执行：用户总能自己构建，或从别人构建的副本获得。

**【判断】** 能收钱的是三类东西：

| 类型 | 例子 | 为什么能收费 |
|---|---|---|
| 持续服务 | iCloud 同步、冲突处理、跨设备恢复 | 需要账号体系、配额、长期维护，fork 不会自动拥有 |
| 持续内容 | 模板库、技能库、行业格式包 | 是内容生产，不是代码；更新节奏本身就是价值 |
| 省事 | 签名公证、商店账单、自动更新、支持 | 用户为「不用自己折腾」付费 |

**【判断】** 这也与开源版的定位自洽：开源版全功能 + 自带 key，用户买的是「自己承担配置成本」；商店版付费，买的是「同步不出事、模板有人更新、出问题有人管」。不要试图用功能阉割来逼付费——那会同时激怒开源用户和商店评论。

## 2. 买断 vs 订阅

| 维度 | 非消耗型买断（一次性解锁） | 自动续期订阅 |
|---|---|---|
| 用户心理 | 一次付清，抵触小 | 需要持续证明价值，否则退订 |
| 收入形态 | 前期集中，后期靠新增 | 稳定，但依赖留存 |
| 与同步的匹配度 | 高：同步是「一次性能力」，维护成本相对固定 | 中：只有持续投入（多端、协作）才撑得住 |
| 与模板/技能库的匹配度 | 低：内容持续更新时买断会亏 | 高：天然适合持续更新 |
| 审核复杂度 | 低：一个商品、恢复购买即可 | 高：订阅组、续订页、价格调整规则 |
| 老用户处理 | 简单：买过永久有效 | 复杂：涨价、降级、宽限期都要设计 |

**【判断】建议：1.1 先上「同步买断」（非消耗型），模板/技能库先按「内容包」卖；等模板更新节奏稳定（例如连续两个季度有实质更新），再考虑把模板做成订阅。**

理由：

1. 同步的成本主要是开发与兼容维护，不是按次计费，买断在商业上说得通。
2. 首版付费的最大风险是「收不到钱还挨骂」，买断的决策成本远低于订阅。
3. 订阅需要持续的版本叙事；在用户基数还小的时候，退订率会把收入打回原形。

**【待核实】** 具体价格档位（Apple 价格点、人民币对应价、是否设首购优惠）需要你按 Apple 最新价格表确认后填写；本文不给数字，避免引用过期档位。

## 3. 小企业计划（15% 抽成）

**【待核实，以 Apple 最新条款为准】** 公开条件大致是：

- 上一自然年（所有 App 合计）的收益不超过 100 万美元；
- 新开发者从未超过该门槛即可申请；
- 需要 Account Holder 在 App Store Connect 主动加入，且每年确认资格；
- 加入后符合条件的交易佣金为 15%，未加入为 30%；
- 超过门槛的次年退出该计划。

**【判断】** 对本项目的实际影响：

- 早期收入远低于门槛，15% 与 30% 的差别是「每 100 元多留 15 元」，值得申请，且申请不影响审核。
- 小企业计划按「账号下全部 App」计算，不按单个 App；如果同账号还有其他产品，需要合并计算。
- 中国区商店同样适用该佣金结构，但税务与结算信息要单独准备。
- 加入后不要假设永久有效：每年复核，收入增长后要预留佣金回到 30% 的预算。

## 4. IAP 商品设计

### 4.1 商品类型选择

| 商品 | 类型 | 适用条件 | 不适用的情况 |
|---|---|---|---|
| iCloud 同步解锁 | 非消耗型 | 一次购买永久解锁；功能边界清晰；无需按时间计费 | 未来同步变成重服务（大容量、协作）时，买断会亏 |
| 模板/技能内容包 | 非消耗型（按包） | 内容一次性交付、版本稳定 | 需要持续更新且更新是卖点时 |
| 模板/技能订阅 | 自动续期订阅 | 每月/每季有可感知的新内容；有明确的续订价值 | 更新频率不稳定、内容一次性 |
| 同步 + 内容订阅包 | 自动续期订阅 | 两类价值都持续，且希望提高客单价 | 早期用户基数小、退订风险高 |
| 消耗型 / 非续期订阅 | 不建议 | — | 与产品形态不匹配，恢复购买与续订体验差 |

**【判断】** 首选组合：

1. **1.1：非消耗型「iCloud 同步」**（永久解锁），配「恢复购买」。
2. **1.1 同期：2–3 个非消耗型内容包**（如「短剧模板包」「电影剧本格式包」「行业技能包」），单独售卖。
3. **观察 1–2 个季度后再评估订阅**，把同步 + 全部内容打包成订阅，作为高价档。

### 4.2 商品配置要点（判断 + 待核实）

- 非消耗型商品要提供「恢复购买」入口，否则审核会拒（3.1.1 相关要求）。
- 同步解锁建议**关闭家庭共享**：CloudKit 私有库按 Apple ID 隔离，家庭共享会造成「家人解锁了但数据不同步」的困惑。
- 订阅若上线，必须有订阅组、续订说明、取消入口，并在 App 内可管理订阅。
- 所有数字内容功能必须走 IAP，**不要在商店版里放站外购买链接或引导**（3.1.1）。
- 1.0 不要出现「即将收费」的占位文案或隐藏开关，避免 2.3.1（隐藏功能）与「虚假宣传」风险。

## 5. 开源版与商店版功能边界

| 能力 | 开源/直售版 | 商店免费版（1.0） | 商店付费版（1.1+） |
|---|---|---|---|
| 编辑器、场景/人物/大纲 | 全部 | 全部 | 全部 |
| 导入 txt/PDF、导出 PDF | 全部 | 全部 | 全部 |
| 本地版本历史、自动保存/恢复 | 全部 | 全部 | 全部 |
| AI 助理（自带 API key） | 全部 | 全部 | 全部 |
| 模型配置与本地 Ollama | 全部 | 全部 | 全部 |
| MCP / CLI 本地桥接 | 全部 | 全部 | 全部 |
| iCloud 同步 | 不含（自行同步文件） | 不含 | 解锁 |
| 内置模板库 | 仓库自带基础模板 | 基础模板 | 完整模板 + 新增内容包 |
| 技能库 | 仓库自带 | 基础技能 | 付费技能包 |
| 自动更新 | Tauri 更新器 | App Store 更新 | App Store 更新 |
| 支持渠道 | GitHub Issues | 商店评论/邮件 | 优先支持（判断是否承诺） |
| 云 AI 代管（未来） | 无 | 无 | 视成本另议 |

**【判断】** 边界原则：**免费版必须是「能完整写完一个剧本」的产品**，付费只增加「跨设备」和「内容供给」，不锁核心写作能力。

## 6. 「1.0 免费 → 1.1 付费」的节奏影响

### 6.1 对现有用户

- **【判断】建议给 1.0 期间的用户「终身免费同步」**（按购买/下载记录或首次启动时间判定），这是最便宜的公关，也是防止早期评论崩掉的手段。
- 若不打算赠送，必须在 1.0 的商店描述里提前写明「同步将在后续版本作为付费功能提供」，否则会被视为事后加锁。
- 开源/直售版用户不受影响：他们本来就没有商店同步，升级路径是「继续用自己的同步方式」。

### 6.2 对评论与评分

- 免费转付费最常见的差评句式是「说好免费，结果要钱」。应对方式只有三种：提前公告、老用户保留、免费版不阉割。
- **【判断】** 1.1 更新说明里把「新增同步（付费）」与「免费功能改进」分开写，明确免费部分没有减少。
- 不要在 1.0 的截图或描述里暗示「所有功能永久免费」，那会成为 1.1 的差评素材。

### 6.3 对审核

- 1.0 免费上架时不要提交 IAP 商品，先走通审核；1.1 再一起提交 IAP 与新版二进制。
- 1.1 提交时 IAP 必须处于「准备提交」并随版本一起审核，否则付费入口会失效。
- **【判断】** 保留同一个 bundle id，不做「新 App 收费、旧 App 下架」；后者会丢掉评论与排名。

## 7. 需要你确认的事项

1. 1.1 的同步是「买断」还是「订阅」——本文建议买断，但最终取决于你对维护成本的判断。
2. 1.0 用户是否赠送终身同步；若不赠送，1.0 描述必须提前写明。
3. 模板/技能包的具体数量、定价与更新承诺（价格需按 Apple 价格档位核实）。
4. 小企业计划的申请时点与账号归属（是否与其它 App 共用账号）。
5. 商店版是否保留 MCP/CLI（当前建议保留；如果担心审核解释成本，可只在直售版提供）。
