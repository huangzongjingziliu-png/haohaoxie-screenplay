# 0.1.58 MCP HTTP transport — protocol-level acceptance (client-level pending)

Scope: in-app Streamable HTTP MCP server on branch `feat/0.1.58-mcp-http` (base `main` @ `5e6ec11`). This record covers the protocol-level pass only. **Client-level acceptance with a real MCP client is not complete** — see the last section.

Environment: macOS 27.2.1, Apple Silicon, ad-hoc signing (`-`), debug app bundle built from this worktree.

## Why a separate bundle identifier was used

An installed 0.1.58 build uses `com.screenplay.studio`. To observe the new build without touching it, the debug bundle was built as:

```
npx tauri build --debug --bundles app --config \
  '{"identifier":"com.screenplay.studio.mcpdev","bundle":{"createUpdaterArtifacts":false},"build":{"beforeBuildCommand":""}}'
```

`beforeBuildCommand` was cleared only to skip sidecar regeneration in this worktree; the frontend assets in the bundle were built by `npm run build`.

## Steps actually run and results

1. **Entitlement present in the built app.** `codesign -d --entitlements -` on the bundle reports `com.apple.security.network.server`. The entitlement is declared in `src-tauri/Entitlements.plist` and referenced from `tauri.conf.json` (`bundle.macOS.entitlements`).
2. **Listener is loopback-only.** After launch, the app listens on `127.0.0.1:8765`; no wildcard binding. Port selection scans 8765–8775 and falls back to an OS-assigned port.
3. **Unauthenticated request rejected.** `POST /mcp` without `Authorization` returns `401`.
4. **DNS-rebinding style Host rejected.** A request with a forged `Host` header returns `403`.
5. **Protocol flow with a valid bearer token** (HTTP probe script, `Accept: application/json, text/event-stream`):
   - `initialize` → `200`, response carried `Mcp-Session-Id`;
   - `notifications/initialized` → `202` with empty body;
   - `tools/list` → `200`, 39 tools;
   - `tools/call` `new_project` → `insert_block` ×3 → `get_document` (revision advanced) → `replace_block` → `save_project`.
6. **Edit reached disk.** The saved `.screenplay` archive (zip) was unpacked and `document.json` contained the replaced text, so the write was not GUI-only state.
7. **GUI reflected the write.** The connection panel shows the address and bearer token with copy buttons; the status bar reported `已保存 rev 5` after the RPC save.
8. **Shutdown leaves nothing behind.** Quitting the app closes the listener: no process is listening on 8765 afterwards and no helper process remains.

## Token persistence (added after the first pass)

Originally the token was regenerated on every launch, which forced clients to reconfigure after each restart. It is now read from a file and reused:

- Path: `~/Library/Application Support/ScreenplayStudio/mcp-http-token` (resolved via `dirs::data_dir()`, the same base directory as `bridge.json`; under App Sandbox this resolves inside the app container).
- Created with mode `0600` (`-rw-------`), contents are 48 hex characters read from `/dev/urandom`.
- Written once: after three separate launches the file mtime stayed at the creation time, and the token was identical each time (`b04fddca…`).
- After each restart, `initialize` with that unchanged token returned `200`, i.e. a client configuration stays valid across restarts.
- The token is reused only if the file content is at least 32 characters and all hex; otherwise it is regenerated and rewritten.

## Not completed: client-level acceptance

A real MCP client has **not** been connected to the endpoint yet, so end-to-end behaviour (client session handling, tool invocation through a client, SSE consumption over a long session) is unverified.

Attempt with Codex CLI 0.163.0 against `http://127.0.0.1:8765/mcp` failed before any tool call:

- Codex exited with `ERROR: workspace routing discovery timed out`.
- The machine's HTTP proxy (`127.0.0.1:7897`) accepts TCP connections but `curl -x 127.0.0.1:7897 https://chatgpt.com` timed out; a direct connection without the proxy also failed. HTTP access to `chatgpt.com` was therefore unavailable during the pass.
- Server-side logs showed the MCP session being created and deleted for the same session id, so the local transport accepted the connection; the turn failed on the model request, not on the MCP endpoint.
- The proxy was not retried repeatedly, and no temporary configuration was left in `~/.codex/config.toml`.
